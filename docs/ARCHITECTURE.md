## 1. Идея и принципы

Современные модели неплохо пишут содержание, но плохо воспроизводят дизайн-систему: ломают сетку, выдумывают шрифты и цвета, теряют логотипы. Поэтому «дизайнера» в сервисе делает не модель, а код, который читает чужой шаблон как набор правил. Модели пишут текст и оценивают смысл.

Из этого следуют пять принципов.

1. **Детерминизм прежде модели.** Размеры, цвета, шрифты, геометрия, подбор кегля и большинство проверок вычисляются без моделей. Сбой модели не ломает вёрстку: разбор шаблона без VLM остаётся полным, а колода без контекстного аудита всё равно собирается и проверяется детерминированно.
2. **Гибрид редактирования шаблона и композиции.** Структурные слайды (титул, раздел, финал) и собственные композиции шаблона клонируются из оригинала: текст пишется прямо в его фигуры, форматирование абзацев сохраняется. Остальные слайды раскладывает композер на «холстах» — слайдах шаблона без контента. Результат собран из материала самого шаблона и не выдаёт генерацию.
3. **Явные артефакты между слоями.** Каждый слой получает и выдаёт типизированную модель (Pydantic) и пишет её JSON на диск. Любой шаг можно воспроизвести и проверить отдельно.
4. **Нативный результат.** PPTX собирается настоящими объектами (тексты, таблицы, диаграммы), а не картинками, и остаётся редактируемым.
5. **Аудит — часть пайплайна.** Проверки работают внутри сервиса, показывают зону замечания на слайде и умеют исправлять то, что пользователь отметил.

Промпты не зашиты в код: это версионируемые файлы скиллов (см. [раздел 10](#10-модели-и-скиллы)). Модель подключается по конфигурации.

## 2. Общая схема

```
 .pptx ──► 1. Разбор шаблона ──► profile.json     дизайн-система, холсты, паттерны
                                     │
 бриф + материалы ─► 2. Сценарий (LLM) ─► content.json     слайды, заголовки, тексты, данные
                                     │
            иллюстрации (GigaChat/Kandinsky), один раз на контент
                                     │
              3. Три варианта + вёрстка ─► plan.json, layouts.json (IR) ─► PPTX ─► PDF ─► PNG
                                     │
              4. Аудит (детерминированный + VLM/LLM) ─► audit.json
                                     │           ▲
                     выбор пользователя ─► исправления ─► пересборка варианта
                                     │
              5. Экспорт ─► PPTX (нативные объекты) · PDF · HTML
```

Системные части:

| Часть | Где | Роль |
|---|---|---|
| Слои обработки | `backend/app/parsing`, `planning`, `layout`, `audit`, `export` | предметная логика |
| Оркестратор | `backend/app/pipeline.py` | порядок слоёв, параллелизм, сроки, события прогресса |
| Клиент моделей и скиллы | `backend/app/llm/`, `backend/skills/` | вызовы моделей, версионируемые промпты, трасса |
| HTTP API | `backend/app/api/main.py` | шаблоны, проекты, SSE-прогресс, превью, исправления, скачивание, раздача фронтенда |
| Командная строка | `backend/app/cli.py` | тот же пайплайн без интерфейса |
| Веб-интерфейс | `frontend/` | мастер, прогресс, проект, аудит, библиотека шаблонов |
| Конфигурация | `config.yaml`, `.env` | модели, пороги, варианты, версии скиллов; секреты |

Внешние программы: **LibreOffice** (рендер PPTX → PDF) и **PyMuPDF** (PDF → PNG и SVG; работает под общим замком, потому что не потокобезопасен).

## 3. Данные между слоями

Слои обмениваются только этими моделями:

| Модель | Файл | Что содержит | Кто пишет → кто читает |
|---|---|---|---|
| `TemplateProfile` (`parsing/model.py`) | `profile.json` | палитра, типографика, шкала кеглей, поля и сетка, стили карточек и таблиц, холсты, паттерны, слайды-образцы, нарратив, стиль иллюстраций | разбор → сценарий, вёрстка, аудит |
| `Brief` (`planning/models.py`) | в `job.json` | тема, назначение, аудитория, данные, число слайдов, длительность, язык, режим иллюстраций | пользователь → сценарий |
| `DeckContent` (`planning/models.py`) | `content.json` | слайды с намерением (`intent`), заголовком, пунктами, диаграммой, таблицей, колонками, цитатой, промптом картинки, заметками; список фактов; целевой объём | сценарий → варианты, аудит |
| `VariantPlan` (`planning/models.py`) | `plan.json` | для каждого слайда: рецепт, холст, тон, запасные холсты | варианты → композер |
| `SlideLayout` (`layout/ir.py`) | `layouts.json` | промежуточное представление вёрстки слайда: заполнение слотов, элементы `El` в координатах слайда (EMU), заметки, предупреждения | композер → сборщик, аудит, исправления |
| `AuditReport` / `Issue` (`audit/model.py`) | `audit.json` | замечания: код проверки, важность, слайд, зона `bbox`, признак исправимости | аудит → интерфейс, исправления |
| `JobState` (`pipeline.py`) | `job.json` | статус, этап, события, варианты, версии скиллов, статистика вызовов | оркестратор → API |

**Намерения слайда** (`intent`): `title`, `agenda`, `section`, `bullets`, `cards`, `process`, `timeline`, `stats`, `chart`, `table`, `comparison`, `quote`, `image`, `closing`.

Промежуточное представление (`SlideLayout`) отделяет решения вёрстки от OOXML: композер и исправления работают с ним, и только сборщик знает про формат PPTX.

## 4. Слой 1. Разбор шаблона

`backend/app/parsing/`. Цель: превратить чужой `.pptx` в `TemplateProfile` — набор правил, по которому можно строить новые слайды.

### Стадии разбора (`profile.py`)

| Прогресс | Стадия | Что происходит |
|---|---|---|
| 5% | Шрифты шаблона | извлекаются встроенные шрифты |
| 12% | Структура слайдов | `TemplateAnalyzer` разбирает каждый слайд; недостающие шрифты подкачиваются из Google Fonts и регистрируются для рендера |
| 20% | Рендер шаблона | LibreOffice → PDF → PNG превью |
| 30% | Слайды-картинки | только для растровых шаблонов: дизайн-система восстанавливается по пикселям |
| 50% | Дизайн-токены | палитра, типографика, сетка, стили карточек и таблиц |
| 60% | Холсты | слайд минус контент, с рендером каждого холста |
| 70% | Паттерны шаблона | слайды-образцы, пригодные для клонирования |
| 80% | Разметка моделью | VLM описывает стиль, тон и стиль иллюстраций (необязательно) |
| 100% | Готово | профиль сохранён |

Результат кэшируется по sha256 файла: повторная загрузка того же шаблона мгновенна. Ключ `--force` (CLI) или поле `force` (API) разбирает заново.

### Модули

| Модуль | Что делает |
|---|---|
| `ooxml.py`, `extract.py` | Фигуры с абсолютными координатами (с учётом групп), наследование стилей run → lstStyle → макет → мастер, цвета темы и `clrMap`, заливки |
| `fonts.py` | Встроенные шрифты (EOT/обфусцированные) → TTF, подкачка из Google Fonts, инстансы вариативных шрифтов, метрики через FreeType. Шрифт без кириллицы меряется запасным шрифтом рендерера, отсутствующий жирный — с поправкой на синтетическое утолщение |
| `render.py` | LibreOffice headless с отдельным профилем на вызов → PDF → PNG. Шрифты шаблона регистрируются в сессии (Windows GDI / fontconfig). PyMuPDF — под общим замком |
| `analyze.py` | Для каждого слайда: заголовок, кикер, плашка заголовка; «хром» (фон, логотипы, колонтитулы, линейки, повторяющиеся элементы) против контента; служебные слайды (инструкции, палитры, библиотеки иконок); вид слайда (титул / раздел / план / контент / финал); **повторяющиеся группы** — карточки в подложках или, без подложек, наборы текстов одного стиля, выстроенные в ряд, колонку или сетку, вместе с иконками |
| `tokens.py` | Палитра (цвета, взвешенные по площади и объёму текста; роли: фон, текст, основной, акценты, цвета диаграмм), типографика по ролям, шкала кеглей, сетка и шаг, стили карточек и таблиц |
| `canvases.py` | Холсты: слайд минус контент. По пикселям рендера уточняются свободная область, фон под слотами и ширина заголовка — логотипы бывают «вшиты» в картинку фона |
| `patterns.py` | **Паттерны шаблона.** Слайды-образцы с карточками, строками, крупными цифрами, таблицами, диаграммами или картинкой, пригодные для клонирования. Образец отбрасывается, если после заполнения на нём останется чужой контент: несколько скриншотов, декоративные рамки устройств, большие удаляемые тексты |
| `raster.py` | Шаблоны из слайдов-картинок (экспорт Figma/Canva). Гладкий фон восстанавливается аппроксимацией от рамки слайда. Находятся строки заголовков, их цвет и кегль, белые карточки и акценты. Из этого собирается редактируемый шаблон-заменитель и разбирается обычным путём |
| `vlm_labels.py` | VLM (скилл `template_analyst`) по контактному листу описывает стиль, тон и стиль иллюстраций. Детерминированный профиль остаётся первичным, модель только дополняет |
| `profile.py` | Оркестратор разбора и кэш профилей |

### Что попадает в профиль

- **Палитра:** цвета с весами и ролями, светлый и тёмный фон, цвета текста, основной цвет, акценты, цвета диаграмм, подложка карточек. `Palette.allowed()` — список разрешённых цветов для аудита.
- **Типографика:** гарнитуры заголовка и текста, допустимые кегли, стили ролей (`title`, `subtitle`, `kicker`, `heading`, `body`, `caption`, `number`).
- **Сетка:** типовая контентная область (поля) и шаг.
- **Холсты** (`Canvas`): вид (титул, раздел, финал, план, контент), слоты для текста с координатами, стилем и ёмкостью в символах, контентная область, фон, тёмный или светлый, «чистый» ли холст, оценка пригодности, превью.
- **Паттерны** (`PatternInfo`): вид (карточки, строки, цифры, таблица, диаграмма, картинка), раскладка, число пунктов, роли текста в пункте, что удалить при заполнении, куда можно вставить иллюстрацию.
- **Нарратив шаблона:** есть ли план и разделители, заглавные ли заголовки, есть ли кикеры, нумерация, средняя длина заголовка, тип финала. Планировщик ему следует, аудит его учитывает: если шаблон пишет короткие заголовки-темы, «нет вывода в заголовке» — только совет.

### Растровые шаблоны

Если слайды шаблона — картинки без фигур (экспорт из Figma или Canva), `is_raster` это распознаёт. Тогда из пикселей восстанавливается редактируемый шаблон-заменитель: фон, строки заголовков с цветом и кеглем, карточки и акценты. Он разбирается тем же путём, что и обычный шаблон. Логотипы и картинки исходника в новые колоды не переносятся.

## 5. Слой 2. Сценарий

`backend/app/planning/`, `backend/skills/`. Цель: по брифу получить `DeckContent` — слайды с заголовками, текстом, данными и заметками спикера. Слой ничего не знает о координатах и OOXML.

### Ход планирования (`planner.py: plan_deck`)

1. **Объём.** Пользовательское число слайдов, иначе при заданной длительности выступления ≈1,5 слайда на минуту (в пределах 10–15), иначе 11–14 по богатству брифа.
2. **Скилл `deck_planner`.** Получает бриф, сюжетную арку под назначение (фича, продукт, проект, инициатива, обучение, другое), формат повествования шаблона, ограничения шаблона (длина заголовка, кикеры, число разделов), каталог иконок, правила иллюстраций и заметок. Ответ — JSON с починкой при ошибке разбора.
3. **Нормализация** (`normalize`, `norm_slide`). Ответ модели приводится к моделям слайдов. Числа не из брифа отбрасываются; диаграмма строится только если значения найдены в брифе; таблица — только со строками, чьи числа есть в источнике; слайды с недостающими данными переводятся в более простой вид (`chart` → `stats` → `cards`, `table` → `cards`).
4. **Титул и финал.** Гарантируются всегда: недостающие добавляются.
5. **Разделители.** Ограничиваются нарративом шаблона: не больше 3 при 13+ слайдах, 2 при 9–12, иначе нет.
6. **Добор.** Если слайдов меньше нужного, скилл `deck_extender` дописывает недостающие отдельным коротким вызовом: без повторов тем и пустых слайдов, без титулов, разделителей и цитат.
7. **Обрезка.** Лишние слайды сверх лимита убираются в порядке: цитаты, разделители, содержательные слайды с конца; титул и финал остаются.
8. **Иллюстрации.** Скилл `illustrator` пишет буквальные сцены по теме колоды и тезисам слайда. Режим «обязательно» гарантирует 2–3 слайда с картинкой.
9. **Заметки спикера.** Объём считается от длительности (130 слов в минуту). Пустые и слишком короткие заметки дописывает скилл `speaker_notes`.

### Материалы

К брифу можно приложить файлы — txt, md, pdf, docx, pptx и другие текстовые. `planning/materials.py` извлекает текст (до 20 тыс. знаков на файл, до 30 тыс. в сумме), и он становится частью брифа и источником фактов наравне с введённым вручную.

### Сверка с брифом (`planning/facts.py`)

Каждое число на слайдах — проценты, суммы, количества, сроки, годы — ищется в брифе. Исключения: нумерация («Шаг 2», «01») и очевидные производные в явном обороте («в 3 раза» при «с 4,5 до 1,5 ч»). Список `facts`, который возвращает сам планировщик, источником не считается. Слайды с неподтверждёнными числами до сборки отправляются корректору (`fixer`): он убирает число или заменяет его качественной формулировкой. Так «первые 4 склада» при плане в 12 или «Q3 2026» без дат в брифе не доходят до колоды.

### Сокращение текста

Если текст не влез в макет, `text_condenser` сокращает его под лимит символов конкретного слота (шаг `condense` в оркестраторе).

## 6. Слой 3. Три варианта и вёрстка

`backend/app/planning/variants.py`, `backend/app/layout/`.

### Три варианта

Одна контент-модель раскладывается тремя детерминированными стратегиями. Ось различий — **плотность × способ визуализации**. На этих двух параметрах пользователи чаще всего расходятся с автором шаблона, и они не требуют повторной генерации текста: варианты различимы визуально, но одинаково соответствуют правилам шаблона.

| | Стратегия | Что меняется |
|---|---|---|
| **A · Классический** | `faithful` | Максимум паттернов шаблона, баланс текста и визуала, основной холст шаблона (изредка второй по популярности, как в самом шаблоне) |
| **B · Визуальный** | `visual` | Крупные цифры, диаграммы, иконки и иллюстрации; меньше текста; паттерны с числами и картинками; чередование тёмных и светлых холстов |
| **C · Компактный** | `dense` | Слияние коротких соседних слайдов, таблицы и сравнения вместо карточек, строки вместо карточек, без разделителей; объём при этом не ниже минимума |

Соответствие «намерение → рецепт» для трёх стратегий задано таблицей `RECIPES` в `variants.py`. Например, `bullets` даёт в A маркированный список, в B карточки, в C строки; `comparison` в C превращается в таблицу.

Описание вариантов — в `config.yaml → variants`, поэтому число и состав вариантов настраиваются.

### Выбор основы слайда

1. **`PatternPicker`** оценивает пригодность каждого паттерна шаблона для слайда: вид, число пунктов, ёмкость слотов, наличие картинки. Он штрафует повторы и учитывает стратегию варианта (B любит цифры и картинки, C — таблицы и строки). Если паттерн набрал меньше порога, он не используется.
2. **`CanvasPicker`** выбирает холст, если паттерн не подошёл: по виду слайда, тону и стратегии; для запасных вариантов держит список альтернатив (если на основном не влезает заголовок).
3. Если и холст не подошёл, слайд собирает композер по рецепту.

### Вёрстка

- **Композер** (`recipes.py`) раскладывает рецепт в контентной области холста с шагом сетки шаблона. Рецепты: карточки, строки, компактные строки, список, процесс, таймлайн, крупные цифры, диаграмма, таблица, сравнение, ключевая мысль, картинка с текстом, план, разделитель, титул, финал. Кегли берутся только из шкалы шаблона, текст подгоняется по реальным метрикам шрифта (`textfit.py`), цвета проверяются на контраст WCAG (`style.py`).
- **Заполнение паттернов** (`patterns.py`) пишет текст в фигуры образца, снимает лишние пункты и равномерно раздвигает оставшиеся. Иконки образца заменяются тематическими (Lucide, `icons.py`) в цвете исходной, фото — сгенерированной иллюстрацией с обрезкой cover. Одинаковые роли соседних пунктов получают один кегль.
- **Сборщик** (`builder.py`) собирает PPTX: клоны слайдов, нативные таблицы и диаграммы python-pptx в цветах палитры, иконки, картинки, заметки спикера; затем удаляет исходные слайды шаблона.
- **Иллюстрации** (`images.py`) генерируются GigaChat → Kandinsky в стиле шаблона. Стиль берётся из палитры словами: описание «векторная инфографика, иконки, интерфейс» тянет генератор в схемы с псевдобуквами. Промпт очищается от «3D», чисел, кавычек, названий брендов и слов про схемы и текст — модель рисует их буквально. Результаты кэшируются по хэшу промпта; генерация идёт по одной картинке, при ответе 429 запрос повторяется с нарастающей паузой. Соединение с GigaChat устанавливается без проверки TLS-сертификата (только для этого хоста): сертификаты Минцифры могут отсутствовать в системе.

## 7. Слой 4. Аудит

`backend/app/audit/`. Подробный каталог — в [AUDIT.md](AUDIT.md); здесь общее устройство.

**Два вида проверок.**
Всего 37 проверок: 26 детерминированных и 11 контекстных.

- **Детерминированные** (`deterministic.py`) работают по самому файлу PPTX и пикселям рендера LibreOffice. Размеры текста считаются по настоящим метрикам шрифтов шаблона, контраст — по фону под текстом на рендере, а не по заявленной заливке. Один и тот же слайд всегда даёт один и тот же результат.
- **Контекстные** (11 вопросов «да/нет»; `contextual.py`) задают VLM вопросы по картинке слайда вместе с его текстом и брифом (скилл `slide_auditor`), а LLM по тексту всей колоды (скилл `deck_auditor`) отвечает про единый язык и связность соседних слайдов. Слайды проверяются параллельно.

**Ложные срабатывания фильтруются:** «опечатка» засчитывается, только если слово есть в тексте слайда и правка небольшая; для титула, плана, разделов и финала часть вопросов не применяется; короткие заголовки-темы — формат шаблона, а не ошибка.

**Исправления** (`fixes.py`). Пользователь отмечает исправимые замечания, и `apply_fixes` правит план или IR:
- детерминированные: привести кегль к шкале, вернуть цвет из палитры, заменить шрифт, вернуть элемент в область, перекадрировать картинку, разбить перегруженный слайд, убрать лишние серии диаграммы, удалить дубль;
- через модель: заголовок-вывод, опечатки, неподтверждённые факты, сокращение текста.

После этого вариант пересобирается и проверяется снова. Детерминированный аудит повторяется целиком, контекстный — только по изменённым слайдам; номер ревизии растёт.

## 8. Слой 5. Экспорт

- **PPTX** — нативные объекты на макетах шаблона; результат сборщика.
- **PDF** — рендер LibreOffice того же PPTX.
- **HTML** (`export/html.py`) — один файл: каждая страница PDF превращается в векторный SVG (`get_svg_image`, текст как контуры) во встроенном просмотрщике. Навигация клавишами `←` `→`, `F` — показ на весь экран, `Esc` — выход. К каждому слайду добавлен скрытый текст для экранных дикторов.
- **PNG-превью** — страницы PDF; интерфейс показывает их и отдаёт миниатюры WebP по параметру `?w=`.

## 9. Оркестрация: прогон, сроки, отказы

`backend/app/pipeline.py`. Слои вызываются строго по порядку и обмениваются только моделями из [раздела 3](#3-данные-между-слоями).

### Этапы прогона и события

| Прогресс | Этап (`stage`) | Что происходит |
|---|---|---|
| 4% | `plan` | планировщик пишет сценарий |
| 18–20% | `plan` | сверка чисел с брифом, сценарий готов (в событие кладётся список слайдов) |
| 22% | `images` | иллюстрации генерируются один раз и переиспользуются всеми вариантами (только если есть ключ и слайды-иллюстрации) |
| 30–36% | `compose` | планы трёх вариантов, композиция, сокращение не влезших текстов; при сокращении варианты собираются заново |
| 42% | `build` | сборка PPTX и рендер PDF/PNG трёх вариантов параллельно |
| 70% | `audit` | детерминированный и контекстный аудит вариантов параллельно |
| 93% | `export` | HTML |
| 100% | `done` / `error` | итог |

Каждое событие пишется в `job.json` и уходит подписчикам SSE (`/api/jobs/{id}/events`). Клиент, подключившийся позже, получает накопленные события и затем живой поток.

### Параллелизм

- Три варианта собираются и рендерятся параллельно (`asyncio.to_thread`, число одновременных рендеров ограничено `render.max_parallel`).
- Контекстный аудит идёт параллельно по слайдам, внутри клиента моделей вызовы ограничены семафором `llm.max_concurrency`.
- Иллюстрации генерируются один раз на контент и последовательно (ограничение тарифа GigaChat).

### Сроки

Общий дедлайн `pipeline.deadline_s` (по умолчанию 300 с, требование ТЗ). Контекстный аудит получает срок на 25 секунд раньше (дедлайн минус 25 с): слайды, до которых очередь не дошла, пропускаются, а колоды не теряются и остаются с детерминированным отчётом.

### Отказы и деградация

| Что упало | Что происходит |
|---|---|
| Основная модель не ответила | две попытки на основной модели, затем две на запасной (`gpt-oss-20b`, только для текстовых вызовов); ошибка JSON лечится отдельным запросом на починку |
| Планировщик вернул слишком мало слайдов | добор скиллом `deck_extender`; если он упал — колода без добора |
| Не удалось дописать заметки, иллюстрации или сократить текст | пропускается только этот шаг, колода собирается |
| Нет ключа GigaChat или ошибка генерации | слайды-иллюстрации превращаются в обычные, колода собирается без картинок |
| VLM недоступна при разборе шаблона | профиль остаётся детерминированным, стиль помечается как «VLM недоступна» |
| Упал один из аудитов | остальные отчёты сохраняются, ошибка пишется в лог |
| Ошибка на любом этапе | задача переходит в `error`, сообщение сохраняется, событие уходит в поток |
| Перезапуск сервера посреди прогона | при чтении задача с диска в статусе «идёт» помечается ошибкой «Генерация прервана»; перезапуск — из интерфейса |

## 10. Модели и скиллы

Подробнее о выборе моделей — в [MODELS.md](MODELS.md).

### Клиент (`llm/client.py`)

- Асинхронный OpenAI-совместимый клиент; провайдер задаётся в `config.yaml` (Yandex Cloud AI Studio по умолчанию, можно vLLM или инференс VK).
- Семафор конкурентности, таймауты, повторы, переключение на запасную модель.
- Режим размышлений Qwen отключён через `chat_template_kwargs.enable_thinking=false`: для структурированного JSON он не нужен и только съедает время.
- Устойчивое извлечение JSON (ответ в блоке кода, текст до и после JSON, висячие запятые), при ошибке — один запрос на починку.
- Трасса всех вызовов в `llm_trace.jsonl`: скилл и версия, модель, попытка, время, токены, промпты и ответ; картинки в трассе заменены заглушкой.

### Скиллы (`llm/skills.py`, `backend/skills/`)

Скилл — это файл `backend/skills/<имя>/<версия>.yaml` с описанием, видом (`text` или `vision`), температурой, лимитом токенов и парой промптов (`system`, `user`) с подстановкой `{{переменных}}`. Активная версия каждого скилла задаётся в `config.yaml → skills`. Промпты не правятся на месте: изменение — это новая версия файла. В журнал прогона пишутся имя, версия и хэш промпта.

| Скилл | Активная версия | Роль |
|---|---|---|
| `template_analyst` | v1 | VLM: стиль, тон и стиль иллюстраций по контактному листу шаблона |
| `deck_planner` | v7 | сценарий: структура, заголовки, тексты, данные, заметки |
| `deck_extender` | v1 | добор слайдов до нужного объёма |
| `speaker_notes` | v1 | текст спикера к слайдам без заметок |
| `illustrator` | v1 | промпты иллюстраций по теме колоды и тезисам слайда |
| `text_condenser` | v1 | сокращение текста под лимит символов слота |
| `slide_auditor` | v1 | VLM-аудит слайда по картинке |
| `deck_auditor` | v2 | LLM-ревью колоды: язык и связность |
| `fixer` | v1 | правка содержимого слайда по исходным данным |

История версий `deck_planner` (v1–v7) хранится в репозитории: v5 — жёсткие правила фактов, запрет подписей-заглушек, план совпадает с разделами, деликатные темы; v6 — длительность выступления, заметки к каждому слайду, строгий объём. Список скиллов, версий и описаний отдаёт `GET /api/skills`.

## 11. Хранилище

Сервис не использует базу данных: всё лежит в каталоге данных (`DATA_DIR`, по умолчанию `data/`) в виде файлов.

```
data/
  templates/<sha256[:16]>/     template.pptx, profile.json, preview/, canvases/
  jobs/<дата-время-id>/        job.json, content.json, llm_trace.jsonl,
                               A/ B/ C/: plan.json, layouts.json, audit.json,
                                         deck_<вариант>.pptx/.pdf, <вариант>.html, slides/
  cache/                       кэш картинок, шрифтов, профилей LibreOffice, временных файлов
```

Состояние активных задач держится в памяти процесса (`JobStore`) и дублируется в `job.json`. Список проектов строится по файлам на диске. Идентификатор проекта — время создания и случайный хвост; идентификатор шаблона — начало sha256 файла, поэтому один и тот же шаблон не хранится дважды.

## 12. HTTP API

`backend/app/api/main.py` (FastAPI). Полный перечень методов — в [README](../README.md#6-http-api); интерактивная документация — `/docs`.

Особенности устройства:
- Разбор шаблона идёт в отдельном потоке; статус хранится в словаре `PARSE_STATUS` и отдаётся через `/api/templates/{id}/status`.
- Генерация запускается как асинхронная задача в цикле событий и не блокирует API; прогресс идёт через SSE с пингом каждые 15 секунд.
- Миниатюры считаются лениво (WebP) и кэшируются рядом с исходным PNG; кэш пересоздаётся, если исходник новее.
- `POST /api/jobs/{id}/rerun` создаёт новый проект с тем же брифом на другом шаблоне и по умолчанию переиспользует `content.json`, поэтому сценарий не пересчитывается.
- Тот же процесс раздаёт собранный фронтенд из `frontend/dist`.

## 14. Как расширять систему

| Задача | Что менять |
|---|---|
| Другая модель или провайдер | `config.yaml → llm` (и `LLM_BASE_URL`). Код не меняется, если API OpenAI-совместимый |
| Свой генератор изображений | интерфейс изолирован в `layout/images.py`: реализовать класс с методом `generate` и свойством `enabled`, подставить в `image_generator()` |
| Изменить промпт | новый файл `backend/skills/<имя>/vN.yaml`, затем `config.yaml → skills.<имя>: vN`. Старая версия остаётся для сравнения |
| Новый вариант вёрстки | запись в `config.yaml → variants`; для новой стратегии — колонка в `RECIPES` и правила в `variants.py` |
| Новый рецепт вёрстки | метод `r_<имя>` в `Composer` (`layout/recipes.py`) и строка в `RECIPES`; использовать токены шаблона, `textfit` и `style.py` |
| Новая проверка аудита | функция в `audit/deterministic.py` (или вопрос в `contextual.py`), запись в `audit/catalog.py` (каталог виден интерфейсу и документации), обработчик в `audit/fixes.py`, тест |
| Порог проверки | `config.yaml → audit` |
| Новый формат материалов | функция извлечения в `planning/materials.py` и расширение в `SUPPORTED` |
| Новый экспорт | функция рядом с `export/html.py`, вызов из `run_job` и `fix_variant`, формат в `download` API |

Каждое изменение слоя должно сопровождаться тестом: модульные тесты не требуют моделей, интеграционные — только LibreOffice.

## 15. Принятые решения и компромиссы

- **Шаблон как правила, а не как подсказка модели.** Дизайн извлекается кодом и проверяется кодом. Цена — сложный разбор (шрифты, наследование стилей, группы), выигрыш — предсказуемость и работа на незнакомых шаблонах.
- **Клонирование образцов шаблона плюс композер.** Клоны дают «родной» вид, композер — покрытие случаев, для которых образца нет. Образец отбрасывается, если после заполнения остался бы чужой контент.
- **Варианты различаются вёрсткой, а не текстом.** Три сценария утроили бы стоимость и время и сделали бы варианты несопоставимыми. Одна контент-модель раскладывается тремя стратегиями.
- **Один VLM-endpoint для текста и зрения.** Qwen3.6-35B-A3B мультимодален и отвечает быстро (MoE, ~3B активных параметров), поэтому 30–70 вызовов на три колоды укладываются в 5 минут.
- **Факты только из брифа.** Сверка чисел до вёрстки и проверка `facts_supported` после исключают выдуманные цифры; цена — на бедном брифе сценарий получается качественным, без графиков.
- **Аудит внутри сервиса и с зоной замечания.** Пользователь видит, где проблема, и сам выбирает, что исправлять; автоматически ничего не переписывается.
- **Файлы вместо базы.** Каждый артефакт прогона доступен для проверки и воспроизведения; цена — сервис рассчитан на один процесс и не масштабируется горизонтально без внешнего хранилища.
- **Проверка в LibreOffice.** Он даёт превью и рендер для аудита на любой ОС; отрисовка в PowerPoint может немного отличаться (см. ограничения в README).
- **Иллюстрации через хостинговый сервис.** Это компромисс прототипа; способ перехода на полностью открытый контур описан в [MODELS.md](MODELS.md).
