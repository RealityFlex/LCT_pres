## 1. Идея и принципы

Современные модели неплохо пишут содержание, но плохо воспроизводят дизайн-систему: ломают сетку, выдумывают шрифты и цвета, теряют логотипы. Поэтому «дизайнера» в сервисе делает не модель, а код, который читает чужой шаблон как набор правил. Модели пишут текст и оценивают смысл. Там, где модели доверена композиция слайда (дизайнерский вариант B), она работает в рамках той же дизайн-системы, а геометрию проверяет и чинит код.

Из этого следуют пять принципов.

1. **Детерминизм прежде модели.** Размеры, цвета, шрифты, геометрия, подбор кегля и большинство проверок вычисляются без моделей. Числа из таблиц с данными тоже считает код, модель только формулирует вывод. Сбой модели не ломает вёрстку: разбор шаблона без VLM остаётся полным, а колода без контекстного аудита всё равно собирается и проверяется детерминированно.
2. **Гибрид редактирования шаблона и композиции.** Структурные слайды (титул, раздел, финал) и собственные композиции шаблона клонируются из оригинала: текст пишется прямо в его фигуры, форматирование абзацев сохраняется. Остальные слайды раскладывает композер на «холстах» — слайдах шаблона без контента. Результат собран из материала самого шаблона и не выдаёт генерацию.
3. **Явные артефакты между слоями.** Каждый слой получает и выдаёт типизированную модель (Pydantic) и пишет её JSON на диск. Любой шаг можно воспроизвести и проверить отдельно.
4. **Нативный результат.** PPTX собирается настоящими объектами (тексты, таблицы, диаграммы), а не картинками, и остаётся редактируемым.
5. **Аудит — часть пайплайна.** Проверки работают внутри сервиса, показывают зону замечания на слайде и умеют исправлять то, что пользователь отметил. В режиме Extended thinking исправимые замечания оформления правятся автоматически.

Оформление берётся из одного из двух источников: корпоративного шаблона `.pptx` или встроенного стиля Лекала. Встроенный стиль сам превращается в шаблон и дальше обрабатывается тем же путём. Брендбук (Figma, токены, PDF, логотипы) накладывается поверх любого из них.

Промпты не зашиты в код: это версионируемые файлы скиллов (см. [раздел 11](#11-модели-и-скиллы)). Модель подключается по конфигурации.

## 2. Общая схема

```
 .pptx ─────────────┐
 встроенный стиль ──┼─► 1. Разбор шаблона ──► profile.json     дизайн-система, холсты, паттерны
 (+ брендбук) ──────┘          │
                               │   длинные материалы ─► выжимка (map/reduce)
                               │   таблицы с данными ─► профиль, задача, расчёт ─► analysis.json
                               │   поиск фактов (Википедия) ─► research.json
                               ▼
 бриф + материалы ─► 2. Сценарий (LLM) ─► content.json     слайды, заголовки, тексты, данные
                               │
                     (по желанию) план ─► правка человеком ─► сборка по плану
                               │
            фото Wikimedia Commons / иллюстрации Kandinsky, один раз на контент
                               │
              3. Три варианта + вёрстка ─► plan.json, layouts.json (IR) ─► PPTX ─► PDF ─► PNG
                 (вариант B: модель компонует слайд, критик проверяет по скриншоту)
                               │
              4. Аудит (детерминированный + VLM/LLM) ─► audit.json
                               │           ▲
                 выбор пользователя / Extended thinking ─► исправления ─► пересборка варианта
                 смена визуализации слайда данных ─────────────────────► пересборка слайда
                               │
              5. Экспорт ─► PPTX (нативные объекты) · PDF · HTML
```

Системные части:

| Часть | Где | Роль |
|---|---|---|
| Слои обработки | `backend/app/parsing`, `planning`, `layout`, `audit`, `export` | предметная логика |
| Встроенные стили | `backend/app/styles` | каталог стилей, генератор `.pptx`-пака, подбор стиля по теме |
| Брендбук | `backend/app/brand` | разбор `.fig`, токенов, PDF, картинок; применение к стилю и шаблону |
| Аналитика данных | `backend/app/analytics` | чтение таблиц, профиль датасета, задача, расчёт, рекомендации визуализации, сюжет колоды по данным |
| Поиск фактов и фото | `backend/app/research` | API Википедии и Wikimedia Commons, Яндекс Поиск API |
| Оркестратор | `backend/app/pipeline.py` | порядок слоёв, параллелизм, режимы и сроки, события прогресса, пересборка варианта |
| Клиент моделей и скиллы | `backend/app/llm/`, `backend/skills/` | вызовы моделей, версионируемые промпты, трасса |
| HTTP API | `backend/app/api/main.py` | шаблоны, стили, брендбук, материалы, проекты, SSE-прогресс, план, превью, исправления, скачивание, раздача фронтенда |
| Командная строка | `backend/app/cli.py` | тот же пайплайн без интерфейса |
| Веб-интерфейс | `frontend/` | мастер, прогресс, план, проект, аудит, визуализация, библиотека шаблонов |

Внешние программы: **LibreOffice** (рендер PPTX → PDF) и **PyMuPDF** (PDF → PNG и SVG; работает под общим замком, потому что не потокобезопасен). Для данных и брендбуков добавлены **pandas** и **openpyxl** (таблицы CSV/XLSX) и **zstandard** (блок данных `.fig`).

## 3. Данные между слоями

Слои обмениваются только этими моделями:

| Модель | Файл | Что содержит | Кто пишет → кто читает |
|---|---|---|---|
| `TemplateProfile` (`parsing/model.py`) | `profile.json` | палитра, типографика, шкала кеглей, поля и сетка, стили карточек и таблиц, холсты, паттерны, слайды-образцы, нарратив, стиль иллюстраций; источник (`source`: загруженный шаблон или стиль), `style_id`, моноширинный шрифт | разбор → сценарий, вёрстка, аудит |
| `Brief` (`planning/models.py`) | в `job.json` | тема, назначение, аудитория, данные, число слайдов, длительность, язык, режим иллюстраций; встроенный стиль и свои цвета, приложенные материалы целиком, поиск фактов, датасеты и цели анализа, брендбук и его приоритет, источник картинок, режим генерации | пользователь → сценарий |
| `BrandKit` (`brand/model.py`) | `brands/<id>/brand.json` | цвета с ролями, акценты, шрифты по ролям, логотипы, примеры слайдов, правила, отступы, минимальный размер и охранное поле логотипа, предупреждения | брендбук → стиль или производный шаблон |
| `Insight` (`analytics/analyze.py`) | `analysis.json` | по датасету: природа, профиль `DataProfile`, задачи с баллами, агрегат, факты и ключевые цифры, вывод по умолчанию, 2–3 варианта визуализации, выбранная | аналитика → сценарий, смена визуализации |
| `Research` (`research/web.py`) | `research.json` | запросы, прочитанные статьи, факты с номерами источников, источники | поиск → сценарий, подбор фото |
| `DeckContent` (`planning/models.py`) | `content.json` | слайды с намерением (`intent`), заголовком, пунктами, диаграммой, таблицей, колонками, цитатой, кодом, промптом и запросом картинки, подписью фото и источника, блоком «и что?», данными слайда-аналитики, заметками; список фактов и источников; целевой объём | сценарий → варианты, аудит |
| `Outline` (`planning/outline.py`) | — (через API) | план колоды: тип, заголовок, тезисы и пожелание к каждому слайду | сценарий → человек → сценарий |
| `VariantPlan` (`planning/models.py`) | `plan.json` | для каждого слайда: рецепт, холст, тон, запасные холсты | варианты → композер |
| `SlideLayout` (`layout/ir.py`) | `layouts.json` | промежуточное представление вёрстки слайда: заполнение слотов, элементы `El` в координатах слайда (EMU), заметки, предупреждения | композер / дизайнер → сборщик, аудит, исправления |
| `AuditReport` / `Issue` (`audit/model.py`) | `audit.json` | замечания: код проверки, важность, слайд, зона `bbox`, признак исправимости | аудит → интерфейс, исправления |
| `JobState` (`pipeline.py`) | `job.json` | статус (`queued`, `running`, `outline`, `done`, `error`), режим (`direct` или `outline`), выбранные варианты, этап, события, варианты, версии скиллов, статистика вызовов | оркестратор → API |

**Намерения слайда** (`intent`): `title`, `agenda`, `section`, `bullets`, `cards`, `process`, `timeline`, `stats`, `chart`, `table`, `comparison`, `quote`, `image`, `code`, `closing`.

**Новые поля слайда** (`ContentSlide`): `code` — листинг (`lang`, `text`, `caption`); `image_query` и `image_credit` — запрос фото и подпись «автор, лицензия»; `source_note` — источник цифр для подвала; `data` — датасет, задача, выбранная визуализация и варианты для слайда данных; `why`/`then` с заголовками `why_head`/`then_head` — блок «почему это важно / что из этого следует»; `instruction` — пожелание человека, которое сценарист учитывает при дописывании. У диаграммы (`ChartSpec`) появились типы `scatter`, `stacked_column`, `stacked_bar`, подсветка категорий, подписи осей, формат чисел, границы оси, точки и линия тренда для рассеяния.

Промежуточное представление (`SlideLayout`) отделяет решения вёрстки от OOXML: композер, дизайнер варианта B и исправления работают с ним, и только сборщик знает про формат PPTX. У элемента `El` есть отражение линии (`flip_h`, `flip_v`) и пунктир (`dash`): дизайнер рисует ими стрелки «назад» и схемы.

## 4. Слой 1. Разбор шаблона, стили и брендбук

`backend/app/parsing/`. Цель: превратить чужой `.pptx` в `TemplateProfile` — набор правил, по которому можно строить новые слайды.

### Стадии разбора (`profile.py`)

| Прогресс | Стадия | Что происходит |
|---|---|---|
| 5% | Шрифты шаблона | извлекаются встроенные шрифты |
| 12% | Структура слайдов | `TemplateAnalyzer` разбирает каждый слайд; недостающие шрифты подкачиваются из Google Fonts и регистрируются для рендера |
| 20% | Рендер шаблона | LibreOffice → PDF → PNG превью |
| 30% | Слайды-картинки | только для растровых шаблонов: дизайн-система восстанавливается по пикселям |
| 50% | Дизайн-токены | палитра, типографика, сетка, стили карточек и таблиц |
| 60% | Холсты | слайд минус контент, с рендером каждого холста |
| 70% | Паттерны шаблона | слайды-образцы, пригодные для клонирования |
| 80% | Разметка моделью | VLM описывает стиль, тон и стиль иллюстраций (необязательно) |
| 100% | Готово | профиль сохранён |

Результат кэшируется по sha256 файла: повторная загрузка того же шаблона мгновенна. Ключ `--force` (CLI) или поле `force` (API) разбирает заново. Разбор принимает и свой идентификатор с готовыми полями профиля (`tid`, `extra`): так разбираются паки встроенных стилей и производные шаблоны брендбука, у которых хэш файла нестабилен или палитра известна заранее.

### Модули

| Модуль | Что делает |
|---|---|
| `ooxml.py`, `extract.py` | Фигуры с абсолютными координатами (с учётом групп), наследование стилей run → lstStyle → макет → мастер, цвета темы и `clrMap`, заливки |
| `fonts.py` | Встроенные шрифты (EOT/обфусцированные) → TTF, подкачка из Google Fonts, инстансы вариативных шрифтов, метрики через FreeType. Шрифт без кириллицы меряется запасным шрифтом рендерера, отсутствующий жирный — с поправкой на синтетическое утолщение |
| `render.py` | LibreOffice headless с отдельным профилем на вызов → PDF → PNG. Шрифты шаблона регистрируются в сессии (Windows GDI / fontconfig). PyMuPDF — под общим замком |
| `analyze.py` | Для каждого слайда: заголовок, кикер, плашка заголовка; «хром» (фон, логотипы, колонтитулы, линейки, повторяющиеся элементы) против контента; служебные слайды (инструкции, палитры, библиотеки иконок); вид слайда (титул / раздел / план / контент / финал); **повторяющиеся группы** — карточки в подложках или, без подложек, наборы текстов одного стиля, выстроенные в ряд, колонку или сетку, вместе с иконками. Колонтитул, который шаблон явно пометил именем фигуры (`footer…`), становится слотом `footer`: туда пишется название колоды или подпись источника |
| `tokens.py` | Палитра (цвета, взвешенные по площади и объёму текста; роли: фон, текст, основной, акценты, цвета диаграмм), типографика по ролям, шкала кеглей, сетка и шаг, стили карточек и таблиц |
| `canvases.py` | Холсты: слайд минус контент. По пикселям рендера уточняются свободная область, фон под слотами и ширина заголовка — логотипы бывают «вшиты» в картинку фона |
| `patterns.py` | **Паттерны шаблона.** Слайды-образцы с карточками, строками, крупными цифрами, таблицами, диаграммами или картинкой, пригодные для клонирования. Образец отбрасывается, если после заполнения на нём останется чужой контент: несколько скриншотов, декоративные рамки устройств, большие удаляемые тексты |
| `raster.py` | Шаблоны из слайдов-картинок (экспорт Figma/Canva). Гладкий фон восстанавливается аппроксимацией от рамки слайда. Находятся строки заголовков, их цвет и кегль, белые карточки и акценты. Из этого собирается редактируемый шаблон-заменитель и разбирается обычным путём |
| `vlm_labels.py` | VLM (скилл `template_analyst`) по контактному листу описывает стиль, тон и стиль иллюстраций. Детерминированный профиль остаётся первичным, модель только дополняет |
| `profile.py` | Оркестратор разбора и кэш профилей |

### Что попадает в профиль

- **Палитра:** цвета с весами и ролями, светлый и тёмный фон, цвета текста, основной цвет, акценты, цвета диаграмм, подложка карточек. `Palette.allowed()` — список разрешённых цветов для аудита.
- **Типографика:** гарнитуры заголовка и текста, допустимые кегли, стили ролей (`title`, `subtitle`, `kicker`, `heading`, `body`, `caption`, `number`).
- **Сетка:** типовая контентная область (поля) и шаг.
- **Холсты** (`Canvas`): вид (титул, раздел, финал, план, контент), слоты для текста с координатами, стилем и ёмкостью в символах, контентная область, фон, тёмный или светлый, «чистый» ли холст, оценка пригодности, превью.
- **Паттерны** (`PatternInfo`): вид (карточки, строки, цифры, таблица, диаграмма, картинка), раскладка, число пунктов, роли текста в пункте, что удалить при заполнении, куда можно вставить иллюстрацию.
- **Нарратив шаблона:** есть ли план и разделители, заглавные ли заголовки, есть ли кикеры, нумерация, средняя длина заголовка, тип финала. Планировщик ему следует, аудит его учитывает: если шаблон пишет короткие заголовки-темы, «нет вывода в заголовке» — только совет.

### Уточнения разбора на трудных шаблонах

- **Подписи под фото не становятся заголовком.** На слайдах вида «команда» самый крупный текст — имя под фотографией. Контентный холст отбрасывается, если его слот заголовка уже 15% ширины слайда и вмещает меньше 12 символов: заголовку-выводу там не уместиться (`canvases.py: draft_canvases`).
- **Неоновая палитра тёмных шаблонов.** Если среди цветов нет насыщенного средней светлоты, основным цветом может стать яркий насыщенный (насыщенность > 0,35, светлота ≥ 0,75): лайм или бирюза на тёмном фоне — тоже фирменный цвет (`tokens.py: build_palette`).
- **Градиентные заливки таблиц.** Заливка ячейки вида «градиент» приводится к сплошному среднему цвету, картинка — к отсутствию заливки (`tokens.py: solid_fill`). Тем же правилом пользуется рецепт таблицы для профилей, разобранных раньше.
- **Контраст серий диаграмм.** Цвет серии, почти сливающийся с фоном холста (контраст < 1,6: тёмная серия на тёмном слайде), заменяется акцентом шаблона с контрастом ≥ 2, а не пропадает с диаграммы; серий в палитре всегда не меньше трёх (`layout/style.py: Look._chart_colors`).

### Растровые шаблоны

Если слайды шаблона — картинки без фигур (экспорт из Figma или Canva), `is_raster` это распознаёт. Тогда из пикселей восстанавливается редактируемый шаблон-заменитель: фон, строки заголовков с цветом и кеглем, карточки и акценты. Он разбирается тем же путём, что и обычный шаблон. Логотипы и картинки исходника в новые колоды не переносятся.

### Встроенные стили Лекала

`backend/app/styles/`. Если корпоративного шаблона нет, колода строится во встроенном стиле.

- **Каталог** — 9 стилей в `styles/catalog/*.yaml` (`StyleSpec`): категория (работа, финансы, промо, учёба, консалтинг), настроение, палитра по ролям (фон, подложка, основной, вторичный, акцент, текст, приглушённый, линия, тёмный фон и текст на нём), шрифты заголовка, текста и кода, хром (мотив, вид обложки) и вариант генератора (`editorial`, `bold`, `minimal`, `academic`).
- **Пак** (`generator.py`). Из стиля генерируется обычный `.pptx` из семи слайдов: обложка, план, раздел, три контентных образца, финал. Сетка 960×540 «пикселей» (1 px = 12 700 EMU), поля 64 px, кикер, заголовок, тонкая линия, подвал с номером. Пак проходит через тот же парсер, поэтому рецепты, аудит, исправления и экспорт работают со стилями без изменений. Палитра в профиль записывается из стиля, а не угадывается по площадям (`spec_palette`); в профиле `source = "style"` и моноширинный шрифт для блоков кода.
- **Кэш.** Идентификатор пака — `style-<id>-<хэш описания и версии генератора>`; пак собирается один раз (под замком на идентификатор), дальше берётся из кэша. Первая сборка стиля занимает порядка 10–30 секунд.
- **Свои цвета.** Пользователь задаёт фон, основной, вторичный и вспомогательный цвет. Производные (текст, приглушённый, линии, подложка, тёмный фон) пересчитываются от них (`StyleSpec.with_overrides`).
- **Авто-подбор.** Скилл `style_picker` называет три подходящих стиля по теме, назначению и аудитории; берётся первый, которого не было в трёх последних колодах в стилях Лекала, — иначе все учебные презентации выходили бы в одном стиле. Без ответа модели стиль выбирается по назначению брифа.

В библиотеке шаблонов компании паки стилей не показываются.

### Брендбук

`backend/app/brand/`. Брендбук приходит в любом сочетании файлов (`POST /api/brand`, до 10 файлов по 200 МБ) и сводится в один `BrandKit`.

| Источник | Модуль | Что извлекается |
|---|---|---|
| `.fig` (Figma, «Save local copy») | `fig.py`, `kiwi.py` | Собственный разбор формата без Figma и без сети: ZIP → `canvas.fig` (заголовок `fig-kiwi`, схема kiwi и блок данных deflate/zstd) → плоский список узлов. Цвета — из стилей заливки с именами, переменных-цветов и реальных заливок (вес — площадь); шрифты — из текстовых стилей и текстов макетов (вес — число символов); логотипы — узлы с «logo/лого» в имени: вектор собирается в SVG из геометрии и переводится в PNG, растр берётся из `images/`; примеры слайдов — фреймы 16:9 верхнего уровня |
| JSON дизайн-токенов | `tokens.py` | W3C Design Tokens (`$value`/`$type`), Tokens Studio (`value`/`type`), плоский словарь `{"colors":…, "fonts":…}`; ссылки вида `{colors.primary}` разрешаются; отступы и правила логотипа |
| PDF-гайдлайн | `pdf.py` | Цвета из текста (HEX, RGB, CMYK) с подписями, шрифты документа и упомянутые в тексте, палитра по рендеру страниц (вес — площадь), логотип — крупная картинка с прозрачностью, правила — строки с запретами и требованиями («нельзя», «охранное поле», «минимальный размер») |
| PNG/SVG/JPG, ZIP | `images.py` | Логотипы (по имени файла или прозрачности) и примеры слайдов; палитра по площади цветов |

**Сведение** (`store.py`). Несколько файлов дополняют друг друга: цвета и шрифты берутся из самого точного источника (`.fig` и токены точнее PDF, PDF точнее картинок), логотипы — откуда нашлись (до четырёх; приложенные отдельными файлами идут первыми), правила — из PDF. Роли цветов (основной, вторичный, акценты, фон, текст, приглушённый) назначает `assign_roles`: по именам («primary», «brand», «фон»…), по весу использования, по насыщенности и светлоте. Брендбук кэшируется по хэшу содержимого файлов и версии разборщика и хранится в `data/brands/<id>/`.

**Применение** (`apply.py`).
- **Встроенный стиль:** цвета ролей, шрифты, логотипы для светлого и тёмного фона и сетка (поля, скругление, минимальная высота логотипа, охранное поле) передаются в `StyleSpec.with_overrides`; собирается свой пак. Свои цвета пользователя применяются поверх брендбука.
- **Шаблон компании:** собирается производный шаблон — копия `template.pptx`, в которой тема (`a:clrScheme` accent1–6 и `a:fontScheme`) получает цвета и шрифты бренда; явные цвета фирменных оттенков на слайдах, макетах и мастере заменяются ролями бренда (нейтральные — фон, текст — не трогаются); шрифты заменяются, если шрифт бренда есть в системе (иначе — предупреждение); картинки на месте логотипа шаблона заменяются логотипом бренда с сохранением пропорций. Затем производный шаблон проходит обычный разбор, и дальше пайплайн не отличает его от загруженного. Идентификатор — `<шаблон>-brand-<брендбук>-b|t`; в библиотеке шаблонов такие профили не показываются.

**Приоритет** (`Brief.brand_priority`). По умолчанию (`brand`) брендбук важнее шаблона: меняются цвета, шрифты и логотип. При `template` («важнее шаблон») от брендбука остаются только логотипы. Предупреждения (логотип шаблона не найден, шрифта нет в системе) уходят в событие этапа `brand` и показываются в ходе генерации.

## 5. Слой 2. Сценарий

`backend/app/planning/`, `backend/skills/`. Цель: по брифу получить `DeckContent` — слайды с заголовками, текстом, данными и заметками спикера. Слой ничего не знает о координатах и OOXML.

### Ход планирования (`planner.py: plan_deck`)

1. **Объём.** Пользовательское число слайдов, иначе при заданной длительности выступления ≈1,5 слайда на минуту (в пределах 10–15), иначе при длинном материале (больше 15 тыс. знаков) — 15–20 слайдов по его размеру, иначе 11–14 по богатству брифа.
2. **Скилл `deck_planner`** (v8). Получает бриф, сюжетную арку под назначение (фича, продукт, проект, инициатива, обучение, другое), формат повествования шаблона, ограничения шаблона (длина заголовка, кикеры, число разделов), каталог иконок, правила иллюстраций и заметок. Ответ — JSON с починкой при ошибке разбора.
3. **Нормализация** (`normalize`, `norm_slide`). Ответ модели приводится к моделям слайдов. Числа не из брифа и приложенных материалов отбрасываются; диаграмма строится только если значения найдены в источнике; таблица — только со строками, чьи числа есть в источнике; слайды с недостающими данными переводятся в более простой вид (`chart` → `stats` → `cards`, `table` → `cards`). Пункты колонок, пришедшие объектами, превращаются в текст; листинг кода сохраняется построчно с отступами (до 18 строк).
4. **Титул и финал.** Гарантируются всегда: недостающие добавляются.
5. **Разделители.** Ограничиваются нарративом шаблона: не больше 3 при 15+ слайдах, 2 при 9–14, иначе нет.
6. **Добор.** Если слайдов меньше нужного, скилл `deck_extender` дописывает недостающие отдельным коротким вызовом: без повторов тем и пустых слайдов, без титулов, разделителей и цитат.
7. **Обрезка.** Лишние слайды сверх лимита убираются в порядке: цитаты, разделители, содержательные слайды с конца; титул и финал остаются.
8. **Разнообразие** (`diversify`). Колода из одних карточек читается как шаблон: карточек, как и списков, — не больше трети содержательных слайдов, «плоский» тип (карточки, список, цитата, картинка, цифры) не повторяется два раза подряд. Лишний слайд получает другой тип по смыслу (три и больше годов → таймлайн, противопоставление → сравнение, иначе — реже всего встречавшийся) и указание сценаристу переписать его с сохранением фактов. Слайды с диаграммой, таблицей и кодом не трогаются.
9. **Слайды с кодом** (`ensure_code`, `planning/code.py`). Если в материалах есть код, а в колоде нет ни одного листинга, добавляются 1–2 слайда `code`: фрагменты находятся по виду строк, собираются с подписью («Листинг 1. …»), для Python отступы восстанавливаются по двоеточиям. Слайд встаёт рядом с самым близким по словам, код переносится дословно, сценарист пишет только заголовок-вывод и пояснения.
10. **Тонкие слайды** (`enrich_thin`). Содержательный слайд с одним-двумя тезисами или почти без текста дописывается по брифу и материалам — одним вызовом `slide_writer` вместе со слайдами, сменившими тип на шаге 8.
11. **Иллюстрации.** Скилл `illustrator` (v2) пишет буквальные сцены по теме колоды и тезисам слайда и короткий английский запрос для поиска фото. Режим «обязательно» гарантирует 2–3 слайда с картинкой, «где уместно» — хотя бы одну при 9+ слайдах.
12. **Заметки спикера.** Объём считается от длительности (130 слов в минуту). Пустые и слишком короткие заметки дописывает скилл `speaker_notes`.

### Материалы

К брифу можно приложить файлы — txt, md, pdf, docx, pptx и другие текстовые (до 12 файлов за раз). `planning/materials.py` извлекает текст: до 150 тыс. знаков на файл и до 200 тыс. в сумме. Таблицы (CSV/TSV, XLSX/XLS, табличный JSON и таблицы внутри txt/md) становятся датасетами — см. [раздел 6](#6-интерпретация-данных). Текст материалов целиком хранится в `Brief.source_text`: по нему сверяются числа.

**Длинные материалы** (`planning/digest.py`). Материал до 25 тыс. знаков (`materials.digest_over_chars`) идёт в бриф целиком. Длиннее — читается целиком по кускам: текст режется по строкам на фрагменты ≈8 тыс. знаков (кусок закрывается на заголовке), каждый конспектирует скилл `material_digest` параллельно (разделы, тезисы, термины, этапы, примеры, факты), конспекты сводит `material_merge` в выжимку до 12 тыс. знаков. Строки выжимки с числами, которых нет в исходном тексте, выбрасываются. Сбой одного куска не отменяет остальные.

### Факты из Википедии (`research/`)

Галочка «Факты из интернета» (`Brief.web_search`) запускает исследование темы до планирования. Источник задаётся в `config.yaml → search.provider`: по умолчанию бесплатный API Википедии, по настройке — Яндекс Поиск API (генеративный ответ с источниками, платно), `none` — выключено.

1. Скилл `web_researcher` формулирует запросы (4 на колоду).
2. Полнотекстовый поиск и поиск по названиям статей; нужные статьи из выдачи выбирает скилл `wiki_picker` (без ответа модели — по совпадению слов).
3. До 4 статей читаются целиком (2, если пользователь сам приложил подробный материал больше 10 тыс. знаков: тогда из сети берётся только дополнение — история, применение, примеры).
4. Скилл `wiki_reader` выписывает факты (до 8 со статьи); факт с числом, которого нет в статье, отбрасывается.
5. Факты с номерами источников добавляются в бриф блоком «ДАННЫЕ ИЗ ИНТЕРНЕТА» — их числа становятся «числами брифа» для сверки.
6. После сценария `attach_sources` находит слайды, где стоит характерное число из найденного факта: источник пишется в подвал слайда, ссылки — в заметки спикера; использованные источники сохраняются в `DeckContent.sources`.

Сбой поиска не роняет прогон: колода строится по брифу. Результат лежит в `research.json`, главные картинки прочитанных статей становятся кандидатами в фото.

### Уточняющие вопросы и план перед сборкой

- **Уточнения** (`POST /api/clarify`). Если материал большой (больше 15 тыс. знаков) или бриф совсем короткий, перед запуском показываются до двух вопросов с вариантами ответа. Вопрос об объёме задаётся по правилу (≈12, ≈16 или ≈20 слайдов); остальные пишет скилл `clarifier`, ответ может менять только аудиторию, глубину подачи и акцент. Без модели остаются только вопросы по правилам.
- **План** (`planning/outline.py`). Если выбрано «Сначала показать план» (по умолчанию — для материала больше 15 тыс. знаков), прогон останавливается после сценария в статусе `outline`. Человек правит заголовки, порядок, типы и тезисы слайдов, добавляет и удаляет слайды, пишет пожелание к слайду («сделай таблицей»). По `POST /api/jobs/{id}/build` изменённые и новые слайды дописывает скилл `slide_writer` одним вызовом (листинги кода не переписываются, числа сверяются с источником), неизменённые остаются как есть, и прогон продолжается с готовым контентом.

### Сверка с брифом (`planning/facts.py`)

Каждое число на слайдах — проценты, суммы, количества, сроки, годы — ищется в брифе и приложенных материалах. Исключения: нумерация («Шаг 2», «01») и очевидные производные в явном обороте («в 3 раза» при «с 4,5 до 1,5 ч»). Список `facts`, который возвращает сам планировщик, источником не считается. Слайды с неподтверждёнными числами до сборки отправляются корректору (`fixer`): он убирает число или заменяет его качественной формулировкой. Так «первые 4 склада» при плане в 12 или «Q3 2026» без дат в брифе не доходят до колоды.

### Сокращение текста

Если текст не влез в макет, `text_condenser` сокращает его под лимит символов конкретного слота (шаг `condense` в оркестраторе).

## 6. Интерпретация данных

`backend/app/analytics/`. Цель: по приложенным таблицам получить слайды, которые отвечают на вопрос «что показывают данные и что из этого следует». Код читает таблицы, определяет природу датасета, выбирает задачу и визуализацию и считает все числа; модель только формулирует вывод по уже посчитанным фактам, и её числа сверяются с ними.

### Путь датасета

| Шаг | Модуль | Что происходит |
|---|---|---|
| Приём | `ingest.py` | CSV/TSV (разделитель — тот, что даёт одинаковое число колонок в первых строках; кодировка UTF-8 или cp1251), XLSX/XLS/XLSM (каждый лист), табличный JSON, таблицы внутри txt/md. Из файла получается один или несколько датасетов (`Table`) и текст вокруг таблиц — он идёт сценаристу как контекст. Исходник сохраняется в `data/uploads/` |
| Профиль | `analyze.py: profile, describe` | `DataProfile`: тип колонки (число, дата, категория, текст, идентификатор) и роль (измерение, метрика, время, идентификатор, текст); годы — измерение, а не метрика; пропуски по колонкам, доля пустых ячеек и полных строк; выбросы по IQR (за пределами 1,5 межквартильного размаха, при 8+ значениях); диапазоны и медианы; ось времени и её шаг (внутри дня, день, неделя, месяц, квартал, год); иерархии измерений (каждому значению A соответствует одно значение B, у B 2–30 значений: город → регион) |
| Развёртка | `wide_to_long` | Широкая таблица с периодами в заголовках («Продукт · I кв. · II кв. …») разворачивается, и периоды становятся осью времени |
| Задача | `recommend.py: choose_tasks` | Все выполнимые задачи с баллами и объяснением: динамика, сравнение, структура (доли), распределение, взаимосвязь, справочные значения, качество данных. Природа данных даёт +3 (справочник +2), цель анализа +3,5 той задаче, о которой она говорит. Цель берётся из карточки датасета или из предложения брифа, которое лучше всего совпало с его колонками (`assign_goals`). Журнал событий (много строк в день, меньше полугода) — распределение, а не динамика; таблица с пропусками ≥10% в колонке — сначала качество данных |
| Расчёт | `analyze.py: _timeseries, _comparison, …` | Агрегат, факты, ключевые цифры и вывод по умолчанию. Все числа форматируются один раз в русской записи — сверка находит их на слайде дословно. Длинные ряды агрегируются (по месяцам), больше 12 категорий — первые 11 и «Прочие», мелкие доли объединяются |
| Визуализация | `recommend.py: recommend, build_chart` | 2–3 варианта по убыванию балла, у каждого объяснение «почему», у первого — почему не подошли остальные типы |
| Перекрёстные факты | `cross.py` | Между датасетами — только там, где совпадают ключи: одно и то же измерение (город в выручке и в анкете) → доли одного ключа в обоих; общая ось времени → корреляция по общим периодам; до 4 фактов |
| Слова и сюжет | `story.py` | Скиллы `data_analyst` (слайд на датасет) и `data_story` (сюжет колоды); сверка каждого числа с фактами кода |

Нераспознанный файл (меньше двух строк; ни чисел, ни повторяющихся категорий; нет таблиц с заголовками колонок) в колоду не попадает: в форме его карточка помечена «не распознано» с причиной, в событии этапа `data` он тоже виден с причиной.

### Выбор визуализации

Типы: линейный график, столбцы, сгруппированные столбцы, горизонтальные полосы, гистограмма, кольцевая и круговая, рассеяние с линией тренда (МНК), накопительные столбцы и полосы, таблица, карточки с ключевыми цифрами. Правила по задаче:

- **динамика:** больше 8 точек — линия (сезонность при 24+), до 8 или кварталы и годы — столбцы; несколько рядов одной единицы, складывающихся в итог, — накопительные столбцы; круговая не подходит — периоды не части целого;
- **сравнение и справочник:** длинные подписи (больше 10 символов) или больше 7 категорий — полосы, иначе столбцы; итог из нескольких частей — накопительные полосы; кольцо — только если значения складываются в целое и категорий не больше 6;
- **доли:** кольцо или круговая (круговая — пока секторов не больше пяти), полосы — когда доли нужно точно сравнить;
- **распределение:** гистограмма, альтернатива — медиана, квартили и 90-й процентиль карточками;
- **взаимосвязь:** рассеяние с линией тренда, альтернатива — средняя по группам столбцами;
- **качество данных:** полосы полноты по колонкам, худшая — сверху.

Таблица предлагается, только если в ней не больше 7 строк; если цель просит «таблицу» или «точные значения», её балл растёт. Тип не зависит ни от формата файла, ни от шаблона: `build_chart(insight, type)` собирает любой вариант из одного и того же агрегата, поэтому переключение визуализации не требует пересчёта.

### Слова модели и сверка чисел

Скилл `data_analyst` (v2) для каждого датасета пишет заголовок-вывод, вводную фразу, подписи ключевых цифр, блок «почему это важно / что из этого следует» с короткими заголовками-мыслями и текст спикера. Скилл `data_story` для колоды по данным пишет главную мысль, порядок датасетов и разделы сюжета, связки между слайдами, три ключевые цифры, выводы, рекомендации и финал.

Каждый текст модели проходит сверку (`story.py`):
- числа — только из фактов кода, ключевых цифр и вывода по умолчанию (годы 1990–2035 считаются контекстом периода); «ускорение» и «замедление» — только если они есть в фактах;
- причинные формулировки без доказательства («за счёт», «благодаря», «доказывает», «напрямую зависит») и пустые фразы («требует внимания», «важно учитывать») отбрасываются;
- подпись ключевой цифры берётся только у пункта с тем же значением и не повторяет саму цифру.

Не прошло — подставляется текст кода. **Заметки спикера** проверяются по предложениям: неподтверждённое предложение выпадает само, а не уносит весь текст; числа профиля датасета (строки, выбросы, точки, метод расчёта) тоже посчитаны кодом и считаются подтверждёнными. Если подтверждённых предложений меньше двух, в заметки идут факты кода. В конце заметок — профиль датасета, метод и почему выбрана диаграмма.

### Колода по данным

Если датасетов два и больше или кроме данных нет других материалов, каркас колоды строит код, а модель пишет слова (`story.data_deck`):

титул («Анализ данных: N датасетов») → **«Главное»** (главная мысль и три цифры, каждая дословно — ключевая цифра одного из датасетов, плюс «почему важно / что следует») → **план** (разделы сюжета с главным выводом каждого и пункт «Выводы и решения») → вступление-вопросы (при 4 датасетах и меньше, если модель его дала) → **слайды данных** в порядке сюжета → **выводы** → **рекомендации** → **финал**.

Порядок датасетов предлагает `data_story`; кого модель не назвала, идут в конце в исходном порядке (динамика → сравнение → доли → распределение → связи → справочник → качество данных). Методика — профиль каждого датасета и почему выбрана диаграмма — пишется в заметки последнего слайда данных; отдельного слайда-таблицы о файлах и слайда с ошибкой разбора нет. Без ответа модели выводы собираются из заголовков-выводов датасетов.

Если датасет один и есть другие материалы, колоду пишет обычный сценарист: ему передаются посчитанные факты и указание не делать слайдов с диаграммами по этим датасетам, а слайды данных вставляются после вступления.

### Слайд данных

- Намерение — `chart`, `table` или `stats` в зависимости от выбранной визуализации; заголовок — вывод с числом.
- Подписи осей с единицами, формат чисел, границы оси (проценты — до 100); главное (лидер, пик, худшая колонка) — основным цветом, остальное — приглушённым; на длинных рядах подписи значений снимаются.
- Ключевые цифры — сбоку от диаграммы; источник («Источник: файл») — в подвал слайда или мелкой строкой под контентом.
- **Блок «и что?»** (`recipes.py: takeaway`) — плашка «почему это важно / что из этого следует» под контентом. Если не помещается, она сжимается до компактной, затем до одной строки «что следует», а если не помещается и она — остаётся в заметках. Подпись второй части выбирается по первому глаголу: «Что проверить», «Что сделать», «Чего избегать», «Решение».
- Много категорий с тяжёлым хвостом (больше 12 категорий, хвост за первыми 10 даёт больше 25% итога): вторая часть списка (категории 11–30) — отдельным слайдом-продолжением, а не строкой «Прочие».

Слайды с блоком «и что?» верстает рецепт: паттерны шаблона и дизайнер варианта B их не берут — у образца нет места под вывод.

### Переключение визуализации

На странице проекта у слайда данных есть панель «Визуализация» (`frontend/src/components/VizPanel.tsx`): задача, файл, 2–3 варианта с объяснением, отметка «рекомендовано» и почему не подошли остальные типы. Выбор варианта вызывает `POST /api/jobs/{id}/variants/{vid}/slides/{n}/chart` с `{type}`, и `pipeline.switch_chart`:

1. проверяет, что тип был среди предложенных для этого слайда;
2. берёт расчёт датасета из `analysis.json` и применяет новый тип к слайду (`story.apply_viz`): диаграмма, таблица или карточки;
3. заново подбирает рецепт и холст под новое намерение и компонует один слайд;
4. сохраняет `content.json` и вызывает общую пересборку варианта `rebuild_variant` с изменённым слайдом.

`rebuild_variant` собирает PPTX, PDF и PNG, повторяет детерминированный аудит целиком, а контекстный — только по изменённым слайдам, обновляет HTML и увеличивает номер ревизии. Той же функцией пользуются исправления по выбору пользователя и автоисправление в режиме Extended thinking. Продолжение длинного списка отдельно не переключается.

## 7. Слой 3. Три варианта и вёрстка

`backend/app/planning/variants.py`, `backend/app/layout/`.

### Три варианта

Одна контент-модель раскладывается тремя стратегиями. Ось различий — **плотность × способ визуализации**. На этих двух параметрах пользователи чаще всего расходятся с автором шаблона, и они не требуют повторной генерации текста: варианты различимы визуально, но одинаково соответствуют правилам шаблона.

| | Стратегия | Что меняется |
|---|---|---|
| **A · Классический** | `faithful` | Максимум паттернов шаблона, баланс текста и визуала, основной холст шаблона (изредка второй по популярности, как в самом шаблоне) |
| **B · Дизайнерский** | `visual` | Каждый содержательный слайд компонует модель по дизайн-системе — свои схемы, шевроны, сетки и акценты; затем проверяет себя по скриншоту. План варианта строится по визуальной стратегии (крупные цифры, диаграммы, иконки, чередование тёмных и светлых холстов) без паттернов шаблона |
| **C · Компактный** | `dense` | Слияние коротких соседних слайдов, таблицы и сравнения вместо карточек, строки вместо карточек, без разделителей; объём при этом не ниже минимума |

Соответствие «намерение → рецепт» для трёх стратегий задано таблицей `RECIPES` в `variants.py`. Например, `bullets` даёт в A маркированный список, в B карточки, в C строки; `comparison` в C превращается в таблицу; `code` во всех вариантах — листинг.

Описание вариантов — в `config.yaml → variants`, поэтому число и состав вариантов настраиваются. Можно собрать только один вариант (`variants` в `POST /api/jobs`; в форме — нажатие на карточку A, B или C): так быстрее.

### Выбор основы слайда

1. **`PatternPicker`** оценивает пригодность каждого паттерна шаблона для слайда: вид, число пунктов, ёмкость слотов, наличие картинки. Он штрафует повторы и учитывает стратегию варианта (B любит цифры и картинки, C — таблицы и строки). Если паттерн набрал меньше порога, он не используется. Образец не берётся, если у слайда есть блок «и что?», если в образце больше 50 фигур (инфографика своей темы) или если заголовки пунктов вместе с текстом не влезут в карточку.
2. **`CanvasPicker`** выбирает холст, если паттерн не подошёл: по виду слайда, тону и стратегии; для запасных вариантов держит список альтернатив (если на основном не влезает заголовок).
3. Если и холст не подошёл, слайд собирает композер по рецепту.

### Вёрстка

- **Композер** (`recipes.py`) раскладывает рецепт в контентной области холста с шагом сетки шаблона. Рецепты: карточки, строки, компактные строки, список, процесс, таймлайн, крупные цифры, диаграмма, таблица, сравнение, ключевая мысль (с опорными тезисами), картинка с текстом, листинг кода, план, разделитель, титул, финал. Кегли берутся только из шкалы шаблона, текст подгоняется по реальным метрикам шрифта (`textfit.py`), цвета проверяются на контраст WCAG (`style.py`). Листинг кода ставится на тёмную плашку моноширинным шрифтом стиля, пояснения — справа. Источник цифр и автор фото пишутся в подвал слайда вместо названия колоды: лицензии CC требуют указать автора.
- **Заполнение паттернов** (`patterns.py`) пишет текст в фигуры образца, снимает лишние пункты и равномерно раздвигает оставшиеся. Иконки образца заменяются тематическими (Lucide, `icons.py`) в цвете исходной, фото — иллюстрацией с обрезкой cover. Одинаковые роли соседних пунктов получают один кегль.
- **Сборщик** (`builder.py`) собирает PPTX: клоны слайдов, нативные таблицы и диаграммы python-pptx в цветах палитры, иконки, картинки, заметки спикера; затем удаляет исходные слайды шаблона. Диаграммы: столбцы, полосы, линия, круговая и кольцевая, накопительные (до 8 серий, подписи внутри сегментов цветом, читаемым на заливке), рассеяние (полупрозрачные точки и линия тренда второй серией); подписи осей и единицы, формат чисел, границы оси, подсветка категорий. У горизонтальных полос подпись каждой категории обязательна: кегль подгоняется под шаг строки, а пропуск подписей запрещается (`c:tickLblSkip = 1`) — иначе PowerPoint на невысокой диаграмме показывает подписи через одну.
- **Картинки** (`add_images` в оркестраторе) подбираются один раз на контент по `Brief.image_source`: `auto` — свободное фото Wikimedia Commons, если оно подошло, иначе иллюстрация генератора; `web` — только фото; `generate` — только генерация.
  - **Фото** (`research/photos.py`): кандидаты — поиск Commons по запросу иллюстратора и главные картинки прочитанных статей Википедии. Код отсеивает мелкие (меньше 1000 px), вертикальные, не JPEG/WebP, несвободные лицензии (NC, ND), схемы, карты, логотипы, сканы и снимки политиков; Qwen-vision (скилл `photo_picker`) по контактному листу выбирает одно фото или отказывается. Разные слайды не получают одно и то же фото. Автор и лицензия идут в подвал слайда, ссылка на страницу файла — в заметки.
  - **Иллюстрации** (`images.py`) генерируются GigaChat → Kandinsky в стиле шаблона. Стиль берётся из палитры словами: описание «векторная инфографика, иконки, интерфейс» тянет генератор в схемы с псевдобуквами. Промпт очищается от «3D», чисел, кавычек, названий брендов и слов про схемы и текст — модель рисует их буквально. Результаты кэшируются по хэшу промпта; генерация идёт по одной картинке, при ответе 429 запрос повторяется с нарастающей паузой. Соединение с GigaChat устанавливается без проверки TLS-сертификата (только для этого хоста): сертификаты Минцифры могут отсутствовать в системе.
  - Слайд-иллюстрация, которому не нашлось ни фото, ни рисунка, становится обычным списком.

### Дизайнерский вариант B: модель компонует слайд

`backend/app/layout/freeform.py`, `ff_examples.py`. Включается в `config.yaml → freeform` (`enabled`, `variants: [B]`, `critic`, `attempts`).

**Что рисует модель.** Содержательные слайды типов «список», «карточки», «процесс», «таймлайн», «цифры», «сравнение», «главная мысль» на контентных холстах. Титул, план, разделители, финал, диаграммы, таблицы, слайды с картинкой (модель не видит фото), клоны образцов и слайды с блоком «и что?» остаются за рецептами.

**Дизайн-система для модели** (`Design`). Цвета по ролям (текст, заголовки, приглушённый, основной, акцент, вторичный, подложка, линия, фон), шкала кеглей шаблона по ролям (подпись, текст, вводная, заголовок, число, крупное), шрифты, хром слайда (кикер, заголовок, линия, подвал уже стоят) и контентная область в пикселях слайда 960×540. Модель (скилл `slide_designer`) отвечает примитивами: текст, плашка (прямоугольник, скруглённый, эллипс, шеврон, «домик», ромб, шестиугольник), линия или стрелка, иконка.

**Чтобы соседние слайды не были одинаковыми**, у каждого типа есть ротация композиций (например, для процесса — цепочка шевронов, блоки в два ряда со стрелками, нумерованные строки; для карточек — «бенто», крупные номера над колонками, сетка плашек, колонки с разделителями, нумерованные строки), и композиция двух предыдущих слайдов не повторяется. Модель получает подсказку композиции, образец её геометрии под число пунктов и область контента (сетка 8 px), опорную раскладку рецепта (размеры текста в ней уже проверены по метрикам шрифта) и что стоит на соседних слайдах.

**Код проверяет каждую попытку.** Ответ привязывается к сетке, удерживается в области, кегль подбирается по реальным метрикам шрифта; `repair` и `salvage` раздвигают наложившиеся плашки и ряды, убирают иконки, оторванные от своего текста; `diagnose` находит пустоты, мелкий текст, пропавшие тезисы. Попытка получает штраф: проблемы геометрии ×10, оторванные иконки и пропавшие заголовки пунктов ×5, разреженность +1. Следующая попытка идёт с конкретными замечаниями кода и прошлым вариантом после выравнивания, а не с «попробуй ещё». Остаётся лучшая попытка; если ни одна не стала чистой (штраф ≥ 10), слайд остаётся рецептом (предупреждение `freeform_fallback`, в событии — «рецептом — N»).

**Попытки и дедлайн.** В обычном режиме — до 3 попыток на слайд (`freeform.attempts`), и к 200-й секунде прогона (`pipeline.designer_s`) новые попытки не начинаются, а начатые обрываются: слайд остаётся лучшей чистой попыткой или рецептом. Так три колоды укладываются в 5 минут даже на медленном инференсе. В режиме Extended thinking — 4 попытки (`pipeline.extended.designer_attempts`) без дедлайна. Слайды варианта рисуются параллельно.

**Критик по скриншоту.** После сборки и рендера скилл `slide_critic` (vision) смотрит на картинку каждого нарисованного слайда вместе со списком элементов и диагностикой кода и возвращает исправленный список. Исправление принимается, только если оно не хуже: код его чинит без ошибок, наложений не больше, чем было, и текстов не меньше половины. Изменённые слайды пересобираются. В обычном режиме критик запускается, если до дедлайна прогона больше минуты; в Extended thinking — всегда.

## 8. Слой 4. Аудит

`backend/app/audit/`. Подробный каталог — в [AUDIT.md](AUDIT.md); здесь общее устройство.

**Два вида проверок.**
Всего 37 проверок: 26 детерминированных и 11 контекстных.

- **Детерминированные** (`deterministic.py`) работают по самому файлу PPTX и пикселям рендера LibreOffice. Размеры текста считаются по настоящим метрикам шрифтов шаблона, контраст — по фону под текстом на рендере, а не по заявленной заливке. Один и тот же слайд всегда даёт один и тот же результат.
- **Контекстные** (11 вопросов «да/нет»; `contextual.py`) задают VLM вопросы по картинке слайда вместе с его текстом и брифом (скилл `slide_auditor`), а LLM по тексту всей колоды (скилл `deck_auditor`) отвечает про единый язык и связность соседних слайдов. Слайды проверяются параллельно, у каждого вызова — потолок по дедлайну прогона. Для длинного материала аудитор получает не первые 3500 знаков, а начало брифа и фрагменты, где встречаются слова слайда.

**Уровни замечаний** в интерфейсе: «Предупреждение» (оранжевый), «Замечание» (синий), «Совет» (серый). Аудит подсказывает, что доработать, а не сообщает о поломке, поэтому слово «ошибка» и красный цвет не используются (`frontend/src/lib/format.ts`, `components/Audit.tsx`).

**Ложные срабатывания фильтруются:** «опечатка» засчитывается, только если слово есть в тексте слайда и правка небольшая; для титула, плана, разделов и финала часть вопросов не применяется; короткие заголовки-темы — формат шаблона, а не ошибка.

**Исправления** (`fixes.py`). Пользователь отмечает исправимые замечания, и `apply_fixes` правит план или IR:
- детерминированные: привести кегль к шкале, вернуть цвет из палитры, заменить шрифт, вернуть элемент в область, перекадрировать картинку, разбить перегруженный слайд, убрать лишние серии диаграммы, удалить дубль;
- через модель: заголовок-вывод, опечатки, неподтверждённые факты, сокращение текста.

После этого вариант пересобирается и проверяется снова (`rebuild_variant`). Детерминированный аудит повторяется целиком, контекстный — только по изменённым слайдам; номер ревизии растёт. В режиме Extended thinking исправимые предупреждения и замечания правятся автоматически, кругами с повторной проверкой (см. [раздел 10](#10-оркестрация-прогон-режимы-сроки-отказы)).

## 9. Слой 5. Экспорт

- **PPTX** — нативные объекты на макетах шаблона; результат сборщика.
- **PDF** — рендер LibreOffice того же PPTX.
- **HTML** (`export/html.py`) — один файл: каждая страница PDF превращается в векторный SVG (`get_svg_image`, текст как контуры) во встроенном просмотрщике. Навигация клавишами `←` `→`, `F` — показ на весь экран, `Esc` — выход. К каждому слайду добавлен скрытый текст для экранных дикторов.
- **PNG-превью** — страницы PDF; интерфейс показывает их и отдаёт миниатюры WebP по параметру `?w=`.

## 10. Оркестрация: прогон, режимы, сроки, отказы

`backend/app/pipeline.py`. Слои вызываются строго по порядку и обмениваются только моделями из [раздела 3](#3-данные-между-слоями).

### Этапы прогона и события

| Прогресс | Этап (`stage`) | Что происходит |
|---|---|---|
| 2% | `style` | без шаблона компании: подбор встроенного стиля (или выбранный пользователем) и сборка его пака |
| 2–3% | `brand` | брендбук: параметры стиля или производный шаблон компании; предупреждения — в событии |
| 3% | `plan` | длинный материал читается целиком и сводится в выжимку |
| 3–3,5% | `data` | анализ датасетов: природа, расчёты, визуализация (в событие кладётся карточка каждого датасета, включая нераспознанные с причиной) |
| 3,5–4% | `research` | поиск фактов в Википедии (в событие кладутся источники) |
| 4% | `plan` | планировщик пишет сценарий |
| 10% | `data` | колода по данным: сюжет, главная мысль, выводы |
| 18–20% | `plan`, `data` | сверка чисел с брифом, слайды данных, источники на слайдах; сценарий готов (в событие кладётся список слайдов) |
| 20% | `outline` | только в режиме плана: прогон останавливается и ждёт `POST /api/jobs/{id}/build` |
| 22–25% | `images` | фото Wikimedia Commons, затем иллюстрации генератора; один раз на контент, общие для всех вариантов |
| 30–36% | `compose` | планы вариантов, композиция, сокращение не влезших текстов; при сокращении варианты собираются заново |
| 42% | `build` | сборка PPTX и рендер PDF/PNG вариантов параллельно; у варианта B — дизайнер и критик (свои события) |
| 70% | `audit` | детерминированный и контекстный аудит вариантов параллельно |
| 80–85% | `audit` | только Extended thinking: круги автоисправления |
| 93% | `export` | HTML |
| 100% | `done` / `error` | итог |

Каждое событие пишется в `job.json` и уходит подписчикам SSE (`/api/jobs/{id}/events`). Клиент, подключившийся позже, получает накопленные события и затем живой поток. Поток закрывается на `done`, `error` или `outline`.

### Режимы генерации (`Brief.quality`)

| | Обычный (`normal`) | Extended thinking (`extended`) |
|---|---|---|
| Общий срок | `pipeline.deadline_s` = 300 с: три колоды с аудитом не дольше 5 минут | `pipeline.extended.deadline_s` = 3600 с, фактически без лимита |
| Поиск фактов | не дольше `pipeline.research_s` = 40 с от начала прогона | без лимита |
| Дизайнер варианта B | до 3 попыток на слайд, заканчивает к `pipeline.designer_s` = 200 с | 4 попытки (`designer_attempts`), без дедлайна |
| Критик по скриншоту | если до дедлайна больше 60 с | всегда |
| Контекстный аудит | заканчивается за 25 с до дедлайна | до общего срока |
| Автоисправление | нет: исправления выбирает пользователь | `fix_rounds` = 2 круга: исправимые предупреждения и замечания правятся (`apply_fixes`), вариант пересобирается и проверяется снова (`rebuild_variant`); круг не запускается, если исправлять нечего |

Переключатель режима — в форме новой презентации (`[data-testid=quality]`).

### Параллелизм

- Варианты собираются и рендерятся параллельно (`asyncio.to_thread`, число одновременных рендеров ограничено `render.max_parallel`); слайды варианта B дизайнер рисует параллельно.
- Контекстный аудит идёт параллельно по слайдам, внутри клиента моделей вызовы ограничены семафором `llm.max_concurrency`.
- Конспекты кусков длинного материала и чтение статей Википедии идут параллельно; датасеты считаются в отдельном потоке и не блокируют API.
- Фото подбираются по очереди (разные слайды не должны получить одно и то же фото), иллюстрации генерируются последовательно (ограничение тарифа GigaChat).

### Сроки

Общий дедлайн обычного режима `pipeline.deadline_s` (по умолчанию 300 с, требование ТЗ). У каждого этапа с моделью свой потолок: поиск фактов — 40 с от начала, дизайнер варианта B — до 200-й секунды, критик — только если до дедлайна больше минуты. Контекстный аудит получает срок на 25 секунд раньше (дедлайн минус 25 с): слайды, до которых очередь не дошла, пропускаются, а колоды не теряются и остаются с детерминированным отчётом. Этап, не успевший к своему сроку, отдаёт то, что успел, или пропускается — прогон его не ждёт (`_bounded`).

### Отмена

`POST /api/jobs/{id}/cancel` отменяет идущую задачу (`asyncio.Task` из `JOB_TASKS`), проект получает статус ошибки с сообщением «Отменено пользователем» и после этого его можно удалить: удаление идущей генерации запрещено (409).

### Отказы и деградация

| Что упало | Что происходит |
|---|---|
| Основная модель не ответила | две попытки на основной модели, затем две на запасной (только для текстовых вызовов и только если запасная задана и отличается от основной); ошибка JSON лечится отдельным запросом на починку |
| Планировщик вернул слишком мало слайдов | добор скиллом `deck_extender`; если он упал — колода без добора |
| Не удалось дописать заметки, тонкие слайды, иллюстрации или сократить текст | пропускается только этот шаг, колода собирается |
| Не прочитался кусок длинного материала | выжимка собирается из остальных кусков |
| Поиск фактов упал или не успел | колода строится по брифу, событие «ничего полезного не нашлось» |
| Не разобрался файл с данными | файл не попадает в колоду, причина видна в карточке и в событии `data` |
| Модель не ответила на этапе данных | заголовки, выводы и заметки — тексты кода; порядок датасетов — исходный |
| Дизайнер варианта B не дал чистого слайда или вышло время | слайд остаётся рецептом |
| Критик предложил худший вариант | исправление не принимается |
| Нет ни фото, ни ключа GigaChat, или ошибка генерации | слайды-иллюстрации превращаются в обычные, колода собирается без картинок |
| Шрифт брендбука не установлен, логотип шаблона не найден | применяется остальное, предупреждение в событии `brand` |
| VLM недоступна при разборе шаблона | профиль остаётся детерминированным, стиль помечается как «VLM недоступна» |
| Упал один из аудитов | остальные отчёты сохраняются, ошибка пишется в лог |
| Ошибка на любом этапе | задача переходит в `error`, сообщение сохраняется, событие уходит в поток |
| Перезапуск сервера посреди прогона | при чтении задача с диска в статусе «идёт» помечается ошибкой «Генерация прервана»; перезапуск — из интерфейса |

## 11. Модели и скиллы

Подробнее о выборе моделей, инференсе и замеренных скоростях — в [MODELS.md](MODELS.md).

### Клиент (`llm/client.py`)

- Асинхронный OpenAI-совместимый клиент; провайдер и модели задаются в `config.yaml` (по умолчанию Yandex Cloud AI Studio) и переопределяются переменными окружения `LLM_BASE_URL`, `LLM_TEXT_MODEL`, `LLM_VISION_MODEL`, `LLM_FALLBACK_MODEL`; для эндпоинтов, которые требуют заголовок `Project-ID`, — `LLM_PROJECT_ID`. ## 12. Хранилище

Сервис не использует базу данных: всё лежит в каталоге данных (`DATA_DIR`, по умолчанию `data/`) в виде файлов.

```
data/
  templates/<sha256[:16]>/     template.pptx, profile.json, preview/, canvases/
  templates/style-<id>-<хэш>/  профиль пака встроенного стиля
  templates/<id>-brand-<bid>-b|t/   производный шаблон в стиле брендбука (derived.pptx, profile.json)
  brands/<bid>/                brand.json, логотипы и рендеры источников
  uploads/<sha256[:16]>__<имя> исходники файлов с данными
  jobs/<дата-время-id>/        job.json, content.json, llm_trace.jsonl,
                               analysis.json (датасеты), research.json (факты из сети), photos/,
                               A/ B/ C/: plan.json, layouts.json, audit.json,
                                         deck_<вариант>.pptx/.pdf, <вариант>.html, slides/
  cache/                       кэш картинок, шрифтов, паков стилей (styles/), профилей LibreOffice,
                               временных файлов, трасса уточняющих вопросов
```

Состояние активных задач держится в памяти процесса (`JobStore`) и дублируется в `job.json`; идущие задачи для отмены — в `JOB_TASKS`. Список проектов строится по файлам на диске. Идентификатор проекта — время создания и случайный хвост; идентификатор шаблона — начало sha256 файла, поэтому один и тот же шаблон не хранится дважды. Брендбук и датасет тоже адресуются хэшем содержимого.

## 13. HTTP API

`backend/app/api/main.py` (FastAPI). Полный перечень методов — в [README](../README.md#6-http-api); интерактивная документация — `/docs`.

Методы, появившиеся вместе с новыми возможностями:

| Метод | Назначение |
|---|---|
| `GET /api/styles` | каталог встроенных стилей: палитра, шрифты, мотив, готов ли пак |
| `POST /api/styles/resolve` | стиль и свои цвета → `template_id` (первый раз собирает пак) |
| `GET /api/styles/{sid}/preview/{n}.png` | превью слайда пака стиля |

| `POST /api/materials` | текст и датасеты из файлов (до 12): для таблиц — `dataset {id, tables[]}` с профилем, задачей и визуализацией или причиной «не распознано» |

| `POST /api/jobs/{id}/variants/{vid}/slides/{n}/chart` | другая визуализация слайда данных из предложенных: `{type}` |

Особенности устройства:
- Разбор шаблона идёт в отдельном потоке; статус хранится в словаре `PARSE_STATUS` и отдаётся через `/api/templates/{id}/status`. Несколько шаблонов разбираются параллельно, каждый в своём потоке.
- Генерация запускается как асинхронная задача в цикле событий и не блокирует API; прогресс идёт через SSE с пингом каждые 15 секунд.
- `GET /api/jobs/{id}/variants/{vid}` у слайда данных отдаёт поле `data`: задача, выбранная визуализация, варианты, профиль, файл — по нему фронтенд строит панель «Визуализация».
- Миниатюры считаются лениво (WebP) и кэшируются рядом с исходным PNG; кэш пересоздаётся, если исходник новее.
- `POST /api/jobs/{id}/rerun` создаёт новый проект с тем же брифом на другом шаблоне и по умолчанию переиспользует `content.json`, поэтому сценарий не пересчитывается.
- `GET /api/templates` не показывает паки стилей и производные шаблоны брендбука.
- Тот же процесс раздаёт собранный фронтенд из `frontend/dist`.

## 14. Фронтенд

`frontend/`: React 19, Vite, Tailwind 4 с токенами VKUI (палитра VK), `@vkontakte/icons`, `@vkontakte/vk-bridge`, TanStack Query. В мини-приложении `vk-bridge` даёт тему ВК, скачивание файлов и «поделиться». Сборка использует относительные пути (`base: "./"`), поэтому работает и из FastAPI, и с хостинга мини-приложений.

**Экраны** (`src/pages/`):

| Экран | Назначение |
|---|---|
| Главная (`Home`) | вход в сервис и сводная статистика (`/api/stats`) |
| Новая презентация (`NewProject`) | оформление → бриф → запуск; черновик брифа хранится в `localStorage` |
| Проекты (`Projects`) | список проектов |
| Проект (`Project`) | ход генерации, редактор плана, вкладки A/B/C, лента слайдов, просмотр, аудит с выбором исправлений, панель «Визуализация» у слайдов данных, сравнение вариантов, показ, экспорт, «Новая презентация в этом стиле» |
| Шаблоны (`Templates`, `TemplateDetail`) | библиотека шаблонов (загрузка нескольких разом) и разобранная дизайн-система |

**Новая презентация:**
- **Оформление:** переключатель «Шаблон компании» (первый и по умолчанию) или «Стиль Лекала» — галерея встроенных стилей с мгновенным эскизом на клиенте, «Авто — подберу по теме» и своими цветами (`StyleGallery`). Ниже — необязательный блок брендбука (`BrandCard`): карточка с палитрой по ролям, шрифтами, логотипами, правилами и предупреждениями; для шаблона компании — выбор «важнее брендбук» или «важнее шаблон (только логотип)».
- **Материалы:** у файла с данными — карточка датасета: задача, предлагаемая визуализация, строки × колонки, ось времени, измерения, метрики, пропуски и поле «Цель (необязательно)»; нераспознанный файл помечен «Не распознано» с причиной.
- **Параметры:** режим генерации «Обычный» / «Extended thinking» (`[data-testid=quality]`); «Факты из интернета» (Википедия); источник картинок — «Фото, иначе рисунок», «Только фото», «Нарисовать».
- **Запуск:** нажатие на карточку A, B или C оставляет только этот вариант; галочка «Сначала показать план»; перед запуском при большом материале или коротком брифе — окно «Пара уточнений».

**Общие компоненты:** `Generation` (этапы и заготовки вариантов по SSE; необязательные этапы — брендбук, анализ данных, поиск фактов, иллюстрации; предупреждения брендбука и источники фактов), `OutlineEditor` (план: перетаскивание, тип, заголовок, тезисы, пожелание к слайду, добавление и удаление, «Собрать презентацию»), `VizPanel` (панель «Визуализация»), `Audit` (панель аудита: уровни «Предупреждение», «Замечание», «Совет»), `Viewer` (просмотр и показ), `SlideStack`, `CommandPalette`, `Cards` (карточки и загрузка шаблона: `Dropzone multiple` разбирает несколько файлов параллельно, у каждого своя строка с прогрессом), `StyleGallery`, `BrandCard`. API-клиент — `src/lib/api.ts`. Вёрстка адаптивная: на десктопе боковая панель, на телефоне нижняя навигация и нижние листы.

## 15. Как расширять систему

| Задача | Что менять |
|---|---|
| Другая модель или провайдер | `config.yaml → llm` или переменные `LLM_BASE_URL`, `LLM_TEXT_MODEL`, `LLM_VISION_MODEL`, `LLM_FALLBACK_MODEL`, `LLM_PROJECT_ID`. Код не меняется, если API OpenAI-совместимый |
| Свой генератор изображений | интерфейс изолирован в `layout/images.py`: реализовать класс с методом `generate` и свойством `enabled`, подставить в `image_generator()` |
| Изменить промпт | новый файл `backend/skills/<имя>/vN.yaml`, затем `config.yaml → skills.<имя>: vN`. Старая версия остаётся для сравнения |
| Новый вариант вёрстки | запись в `config.yaml → variants`; для новой стратегии — колонка в `RECIPES` и правила в `variants.py`; послайдовый дизайн для варианта — `config.yaml → freeform.variants` |
| Новый рецепт вёрстки | метод `r_<имя>` в `Composer` (`layout/recipes.py`) и строка в `RECIPES`; использовать токены шаблона, `textfit` и `style.py` |
| Новая композиция дизайнера | строка в `HINTS` (`layout/freeform.py`) и генератор образца в `layout/ff_examples.py` |
| Новый встроенный стиль | файл `backend/app/styles/catalog/<id>.yaml` (`StyleSpec`); пак соберётся при первом использовании |
| Новый формат брендбука | функция `brand_from_<формат>` в `backend/app/brand/`, вид файла в `store.kind_of` и его ранг точности в `RANK` |
| Новая аналитическая задача или тип визуализации | расчёт в `analytics/analyze.py` (и `build_task`), баллы в `recommend.choose_tasks`/`recommend`, сборка в `build_chart`, тип диаграммы в `ChartSpec` и сборщике |
| Новый источник фактов | ветка в `research/web.py: research` и значение `config.yaml → search.provider` |
| Новая проверка аудита | функция в `audit/deterministic.py` (или вопрос в `contextual.py`), запись в `audit/catalog.py` (каталог виден интерфейсу и документации), обработчик в `audit/fixes.py`, тест |
| Порог проверки | `config.yaml → audit` |
| Сроки и режимы | `config.yaml → pipeline` (`deadline_s`, `research_s`, `designer_s`, `extended`) |
| Новый формат материалов | функция извлечения в `planning/materials.py` и расширение в `SUPPORTED`; для таблиц — `analytics/ingest.py` |
| Новый экспорт | функция рядом с `export/html.py`, вызов из `run_job` и `rebuild_variant`, формат в `download` API |

Каждое изменение слоя должно сопровождаться тестом: модульные тесты не требуют моделей, интеграционные — только LibreOffice. Для новых частей есть отдельные наборы: `test_analytics.py`, `test_recommend.py`, `test_brand.py`, `test_styles.py`, `test_research.py`, `test_code.py`.

## 16. Принятые решения и компромиссы

- **Шаблон как правила, а не как подсказка модели.** Дизайн извлекается кодом и проверяется кодом. Цена — сложный разбор (шрифты, наследование стилей, группы), выигрыш — предсказуемость и работа на незнакомых шаблонах.
- **Клонирование образцов шаблона плюс композер.** Клоны дают «родной» вид, композер — покрытие случаев, для которых образца нет. Образец отбрасывается, если после заполнения остался бы чужой контент.
- **Варианты различаются вёрсткой, а не текстом.** Три сценария утроили бы стоимость и время и сделали бы варианты несопоставимыми. Одна контент-модель раскладывается тремя стратегиями.
- **Модель-дизайнер под контролем кода.** Вариант B даёт композиции, которых нет в рецептах, но каждая попытка проверяется геометрически, а критик по скриншоту не может сделать слайд хуже. Цена — время и вызовы модели, поэтому у дизайнера свой дедлайн и запасной путь — рецепт.
- **Встроенный стиль — тоже шаблон.** Стиль генерирует обычный `.pptx` и проходит тот же разбор, а брендбук превращает шаблон компании в производный шаблон. Так у пайплайна один вход, и все проверки работают одинаково.
- **Данные считает код, слова пишет модель.** Природа датасета, задача, тип диаграммы и все числа определяются правилами и воспроизводимы; модель пишет вывод и интерпретацию, а её неподтверждённые числа и причинные формулировки отбрасываются. Цена — шаблонные формулировки, когда модель не ответила.
- **Один мультимодальный Qwen для текста и зрения.** Разметка шаблона, подбор фото, критик и аудит по картинке идут тем же endpoint, что и тексты. Поэтому на инференсе VK основной — Qwen: модель, которая быстрее отвечает, но не принимает картинки, не закрыла бы vision-скиллы (см. [MODELS.md](MODELS.md)).
- **Два режима вместо одного компромисса.** Обычный режим держит требование ТЗ (три колоды за 5 минут) потолками времени на каждом этапе; Extended thinking снимает лимит ради лучшего результата: больше попыток дизайнера, критик всегда, автоисправление оформления.
- **Факты только из источников.** Сверка чисел до вёрстки и проверка `facts_supported` после исключают выдуманные цифры; источниками служат бриф, приложенные материалы, посчитанное по данным и, по желанию, Википедия с подписью источника. Цена — на бедном брифе без поиска сценарий получается качественным, без графиков.
- **Аудит внутри сервиса и с зоной замечания.** Пользователь видит, где проблема, и сам выбирает, что исправлять; автоматически правится только оформление и только в режиме Extended thinking.
- **Файлы вместо базы.** Каждый артефакт прогона доступен для проверки и воспроизведения; цена — сервис рассчитан на один процесс и не масштабируется горизонтально без внешнего хранилища.
- **Проверка в LibreOffice.** Он даёт превью и рендер для аудита на любой ОС; отрисовка в PowerPoint может немного отличаться (см. ограничения в README).
- **Иллюстрации через хостинговый сервис.** Это компромисс прототипа; способ перехода на полностью открытый контур описан в [MODELS.md](MODELS.md). Свободные фото Wikimedia Commons снижают зависимость от генератора.
